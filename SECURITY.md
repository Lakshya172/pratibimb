# Security Policy — PratiBimb

PratiBimb is a privacy product. **Its Git history is part of its threat surface.** A secret
committed and then deleted is still in the history, still in every clone, and still in
every fork. Treat a commit as irreversible publication.

---

## 1. What must NEVER enter this repository

| Category | Examples |
|---|---|
| **Credentials** | API keys, OAuth tokens, `HF_TOKEN`, passwords, session cookies, model-host credentials |
| **Key material** | `.pem`, `.key`, `.p12`, `.pfx`, private certificates |
| **Real personal data** | Any real Aadhaar, PAN, GSTIN, IFSC, UPI VPA, phone number, email, address, DOB, photograph, or account number — **including your own** |
| **Real captures** | Screenshots or page dumps taken from a real logged-in session, a real government portal, or a real banking page |
| **User data** | Browsing history, vault dumps, ledger exports containing plaintext |
| **`.env`** | Only `.env.example`, which contains no values |
| **Model weights** | `.onnx`, `.safetensors`, `.gguf`, `.bin`, `.pt`. Reference them by pinned revision; never vendor them. |

`.gitignore` enforces most of this mechanically. **`.gitignore` is a safety net, not the
policy.** The policy is: look at what you are staging.

## 2. Synthetic fixtures only

Every identifier used in a test, a fixture, an experiment or a demonstration is
**generated**, never real. This is not only a privacy rule — it is also how the evaluation
set gets free ground-truth boxes (`docs/testing/benchmark-contract.md`).

- Aadhaar fixtures must be **Verhoeff-valid but not issued** — generated by our own
  generator, never copied from a document.
- The false-positive decoy set exists precisely so that lookalikes can be tested without
  ever touching a real identifier.
- If an experiment appears to require real PII, **that is a stop condition.** Halt and
  escalate; do not proceed with a redacted or partial real value.

## 3. Pre-commit inspection — required

Before every commit:

```bash
git status --short          # what is being added
git diff --cached           # what those files actually contain
scripts/check-secrets.sh    # mechanical scan of the staged set
```

`scripts/check-secrets.sh` is advisory and pattern-based. **It cannot prove the absence of
a secret.** It catches the common shapes; you are responsible for the rest.

## 4. Security invariants live in code review, not in this file

The 25 system-level invariants — the egress invariant, the payload pin, the memory-only
vault, fail-closed verification — are specified in
**[`docs/security/security-invariants.md`](docs/security/security-invariants.md)** and the
threat model in **[`docs/security/threat-model.md`](docs/security/threat-model.md)**.

Any pull request touching the vault, the verifier, the egress module, the manifest, the
action validator, or logging requires review by the `privacy-security-engineer` role, which
holds a **standing veto**. That veto is not overridden by schedule pressure.

## 5. Stop conditions

Halt work immediately and escalate — do not work around — on discovering any of:

- Egress can bypass the single egress module.
- Sensitive data can leave before verification.
- A payload can be mutated between verification and transmission.
- Arbitrary code execution, `eval`, or a shell path becomes necessary.
- A secret would be required in source control.
- An experiment would require real PII.
- The exact browser execution context cannot be reproduced.
- A dependency or model licence creates an unresolved legal risk.
- The architecture materially contradicts the dossier.

## 6. Reporting a vulnerability

This repository is a hackathon submission under active development and is **not yet
deployed**. During the build, report security concerns directly to the project architect
and open an issue with the `type:security` label. If a finding involves data that has
already been committed, report it **before** attempting any history rewrite — history
rewriting is an authorized-only operation (`CONTRIBUTING.md` §6).

## 7. Licence risk is a security concern here

The dossier records that v2.0 pinned an **AGPL-3.0** model believing it was MIT. AGPL §13
has network-service implications for software handed to a government department. Every
model's licence is verified **against its pinned revision**, and recorded in
[`agentos/registry/model-registry.md`](agentos/registry/model-registry.md) with the URL and
the date it was read. A licence claimed on a model card is `UNKNOWN` until someone opens
the revision.
