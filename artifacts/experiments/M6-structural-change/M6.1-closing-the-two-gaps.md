## Gap 1 — tracked-element resize

### What changed

§6 names *"ResizeObserver on tracked elements"*. M6 observed `document.documentElement` only,
because two obstacles had not been solved:

| obstacle | what it would have caused | how it is solved |
|---|---|---|
| Re-enumerating the tracked set would be polling | a timer, which the capture policy forbids | the set is re-targeted **inside `measure()`** — the observer follows the element graph, and the graph is rebuilt only when something explicitly asks for an observation |
| A `ResizeObserver` delivers an initial callback per element | every observation instantly stale against itself | **an element's first delivery records its size and reports nothing**; a later delivery is compared against that record |

The baseline rule is the whole of it. There is no window to wait out, no first-callback counter to
get wrong and no clock involved: the question asked is *"does this size differ from the last size I
was told about"*, which is what a resize signal is actually for. Sizes come from the observer's own
`borderBoxSize`, never from `getBoundingClientRect` — the two measure different boxes, and comparing
one against the other would report a change on every callback.

Removed elements are unobserved and their baseline dropped, so an element that returns re-baselines
rather than being compared against a size from before it left. Added elements become tracked at the
next observation, and their **insertion was already a `childList` record**, so nothing about them
goes unnoticed in the meantime.

**The fan-out is reported, not asserted.** `StructuralReading.tracked` carries the number of live
resize observations, taken from the surface that holds them. Measured on this fixture: **7** — the
element graph's own set plus the document element, not the document's node count.

### The measurement that decides it

The third act resizes a tracked element through the **CSSOM**: `sheet.insertRule` changes no node,
writes no attribute, alters no text, and does not touch the `<style>` element's own child. A
`MutationObserver` watching `childList`, `characterData` and every watched attribute across the
entire subtree has **nothing to report**. The element still resizes.

| act | change | seq | Δnodes | Δattributes | Δtext | **Δresizes** |
|---|---|---|---|---|---|---|
| INSERTION | a button appended to a container | 0 → **2** | **+1** | 0 | 0 | +1 *(the container grew)* |
| ATTRIBUTE | `aria-label` on a tracked node | 0 → **1** | 0 | **+1** | 0 | 0 |
| **TRACKED_RESIZE** | a CSSOM rule widening `#target` | 0 → **1** | **0** | **0** | **0** | **+1** |

The third row is the result. The resize counter advanced while every DOM-record counter stood
still, so **only the `ResizeObserver` can have moved the sequence**. The page confirms the element
really changed: `#target` 140 px → **260 px**, read from the page rather than inferred.

The second row is the control: an attribute change moved the attribute counter and **not** the
resize counter, which is what shows the initial-delivery baseline is working — M6's log carried a
spurious `resizes: 1` from the observer introducing itself, and it is gone.

## Gap 2 — the stale refusal, in a browser

M6 recorded `OBSERVATION_STALE` as *"implemented and unexercised in situ"*: eight unit tests, zero
browser occurrences. All three acts now fire it.

Nothing is simulated. No observer callback is invoked by hand, no `stale` flag is set, no witness is
fabricated. The harness changes the page through ordinary DOM and CSSOM calls, the browser's own
observers deliver whatever they deliver, and the **unchanged gates** are then asked to act.

| | INSERTION | ATTRIBUTE | TRACKED_RESIZE |
|---|---|---|---|
| fresh observation is current | `stale: false` | `stale: false` | `stale: false` |
| after the change | `stale: true` | `stale: true` | `stale: true` |
| stale action reached | **VALIDATE** | **VALIDATE** | **VALIDATE** |
| reason | **`OBSERVATION_STALE`** | **`OBSERVATION_STALE`** | **`OBSERVATION_STALE`** |
| witness seen by the gate | `seq 2` vs `observedAtSeq 0` | `1` vs `0` | `1` vs `0` |
| **dispatched** | **false** | **false** | **false** |
| events put into the page | **0 → 0** | **0 → 0** | **0 → 0** |
| page after the refusal | unchanged | unchanged | unchanged |
| after an explicit re-observation | `stale: false` | `stale: false` | `stale: false` |
| the same action then | `VERIFY_RESULT` **CONFIRMED** | `VERIFY_RESULT` **CONFIRMED** | `VERIFY_RESULT` **CONFIRMED** |
| `structurallyCurrent` | `true` | `true` | `true` |
| dispatches, whole act | **exactly 1** | **exactly 1** | **exactly 1** |

The refusal is read three ways rather than one: the gate's own outcome, the page agent's
`firesStarted` count in the world that would have dispatched, and the page's own state. All three
agree that nothing happened.

**The full cycle is demonstrated end to end:** observation current → page changes → observation
stale → action refused → **explicit** re-observation → action proceeds. The refresh is explicit at
every step. Nothing re-observes on its own, and nothing captures.

### It still triggers no capture

**This entire run is on the product build and takes no frame at any point.** The structural signal
and the gates it feeds are DOM-only: there is no capture authority in the path, no ticket is minted,
no stream is opened. The approved capture policy is untouched and unexercised, which is the point —
a change signal that reached for a frame would undo ADR-0009 without anyone editing a policy.

The worker saw **98 messages, 33 848 bytes** across the three acts. The structural reading crossing
it is `{ watching, seq, nodes, attributes, text, resizes, tracked, at }`: booleans, numbers and
`null`. A string cannot appear in it, so page text cannot.

## Gap 3 — the typecheck coverage gap: **closed, with no new dependency**

M6 recorded that `apps/extension` was absent from the TypeScript graph and measured the cost of
entry at **81 errors, every one a missing `chrome` name or namespace**.

**Outcome: option A.** `@wxt-dev/browser` already ships the WebExtension API surface as
`export namespace Browser`, and WXT is in the frozen stack (`constitution.md` §5), so it is already
installed. `apps/extension/types/wxt-globals.d.ts` gives that surface the global name the source
uses and declares WXT's two entrypoint wrappers **from their published module paths**, so nothing
depends on `apps/extension/.wxt/` — which is git-ignored and would have made a fresh clone fail
until something ran `wxt prepare`.

**No dependency was added**, so no dependency-owner decision under `AGENTS.md` §4.6 is required. A
test asserts that `@types/chrome` is absent from `package.json`, so adding it later is a deliberate
act rather than a drift.

`npm run typecheck` is now `tsc -b --force && tsc -p apps/extension/tsconfig.json`. 81 → **0**.

### What it found immediately

Four real defects that had been type-checked by nothing:

| where | defect |
|---|---|
| `host/sidepanel/main.ts` | `const status` collided with `window.status`, a DOM global of type `string`. The file had been typed against the wrong `status` for its whole life |
| `host/offscreen/main.ts` | `fetch` was passed `body: undefined`, which `exactOptionalPropertyTypes` forbids |
| `test/visualBoundary.test.ts` | a `PerceptionSummary` fixture missing `route`, `workerSawPixels` and `text` — the three fields M3.1 and M4 added |
| `test/visualBoundary.test.ts` | an `ElementNode` fixture missing `parent` and `children`; and a `ms` block missing `encode` |

All four are fixed. The last two are exactly the drift the gap was hiding: fixtures that had stopped
describing the types they claim, passing at runtime because nothing checked them.

**What remains explicit** is runtime coverage, not types: `coverageBoundary.test.ts` now requires
every extension source file to be on one of two lists — exercised by a test, or exercised only in a
browser — so a new file forces that decision.
