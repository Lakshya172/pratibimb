## 1 · Measurement tooling — isolated, W1-only, uncommitted

**The recorded toolchain could not be installed as-is.** S-04a-1 recorded `paddle2onnx 2.1.0` +
`paddlepaddle 3.1.0`, but did not record the Python version. `paddle2onnx 2.1.0` publishes Windows
wheels for **cp38–cp312 only**, and W1's only interpreter was Python 3.13 — for which the index offers
`paddle2onnx` up to 0.9.2, which predates the `inference.json` (PIR) format this revision ships.

The owner approved an isolated, user-scoped Python 3.12 for this purpose. Installed:

| | |
|---|---|
| bootstrap | `uv 0.12.19` in a throwaway venv (session scratchpad) |
| interpreter | CPython **3.12.14** (python-build-standalone via uv, `%APPDATA%\uv\python`) — no PATH or registry change. `uv python install` exited 2 while creating a minor-version *link*; the interpreter itself installed and ran |
| venv | session scratchpad, **outside the repository** |
| packages | **paddlepaddle 3.1.0 · paddle2onnx 2.1.0 · onnxruntime 1.29.0** · onnx 1.17.0 · numpy 2.5.3 · pillow 12.3.0 · protobuf 7.36.2 · setuptools 84.0.0 (Paddle imports it; uv venvs omit it) |

The three versions S-04a-1 recorded are matched exactly. The recorded failure mode
(`DLL load failed while importing paddle2onnx_cpp2py_export`) did not occur.
**`package.json`, the lockfile and the extension are untouched.**

### MATCH? — **No, byte-wise. Yes, functionally.**

S-04a-1 recorded **4 819 576 B, sha256 `5f353dec…705b`, 502 nodes**. The reconstruction is
**4 766 440 B, 925 nodes**: 313 `Constant` + 248 `Identity` + 364 compute nodes, with **0
initializers** — the weights are held in `Constant` nodes. The dominant operators match the record
(**62 `Conv`, 24 `HardSwish`**). Same tool versions, different serialisation: the difference is in how
the exporter wrote the graph, not in what it computes.

**The decisive test is functional.** Run through native `onnxruntime 1.29.0` on S-04a-1's exact
synthetic input and compared against S-04a-1's committed `reference.json`:

| | S-04a-1 reference | reconstruction | |
|---|---|---|---|
| count, shape | 409 600, [1,1,640,640] | 409 600, [1,1,640,640] | **equal** |
| min, max | 1.1920929e-07, 1.5199184e-06 | same | **exact** |
| 4 sampled values | — | — | **exact** |
| sumAbs | 0.22270429 | 0.22270218 | rel **9.5e-06** — ~2 000× inside 2e-2 |

**The reconstruction computes the function S-04a-1 measured.** A representation-only variant (the
`Constant` weights lifted to initializers, `Identity` bypassed; 925 → 364 nodes) is byte-identical on
native ORT, which settles that the extra nodes carry no arithmetic.

## 3 · S-04a-1 — the frozen WASM criterion, unchanged

Per output: **count equal** AND **|sumAbs_web − sumAbs_ref| / |sumAbs_ref| ≤ 2e-2**. Web and native
receive the **identical** input bytes, so the comparison isolates the runtime.

| input | count web / ref | sumAbs web | sumAbs ref | **relErr** | max \|web − ref\| | output range | **verdict** |
|---|---|---|---|---|---|---|---|
| **synthetic** (S-04a-1's own) | 409 600 / 409 600 | 0.21353200 | 0.22270218 | **4.118e-02** | 1.79e-07 | 8.9e-08 … 1.5e-06 | **FAIL** |
| **realistic** (S-04a-1a) | 655 360 / 655 360 | 13 339.4499 | 13 339.5063 | **4.233e-06** | 2.27e-04 | 0 … 1 | **PASS** |

**The synthetic failure reproduces S-04a-1 to three significant figures (4.12e-02),** which is what
makes this the same measurement. Its explanation is visible in the row: the synthetic input contains
no text, every output value lies between 1e-7 and 1.5e-6, and the largest absolute disagreement is
**1.8e-07** — the 4% is a ratio of two tiny sums, exactly as S-04a-1's logit analysis argued.

**On a real page the output is a genuine probability map (0 … 1), and web and native agree to
4.2e-06 relative — about 4 700× inside the bound.** That is S-04a-1a, named p1 in September and
never run until now.

**How the two rows combine is left open, deliberately.** The rule was written against the synthetic
input and states no input. Whether the realistic result supersedes the synthetic one for QG-03's WASM
column is a gate-owner judgement. It does not affect this candidate's verdict, which is decided by
§5 regardless.

## 4 · Realistic input

A screenshot of the M7 fixture (`visual.html`, **unchanged since M7**), 1280×720 at DPR 1, so image
pixels are CSS pixels. PNG sha256 `7fb4bb0a…97f8`.

Pre-processed exactly as the pinned `inference.yml` declares: `DecodeImage(BGR)` →
`DetResizeForTest(resize_long=960)` → `NormalizeImage(1/255, ImageNet mean/std, hwc)` → `ToCHW`.
The resize is PaddleOCR's type-2 rule — long side to 960, each side rounded **up** to a multiple of
128 — giving **[1,3,640,1024]** with ratio_h 0.889 and ratio_w 0.800. Bilinear interpolation uses
cv2's `INTER_LINEAR` convention (half-pixel centres, no antialiasing), implemented in numpy. These
reproduce upstream definitions and are not vendored code; they define what "realistic" means and
cannot affect WASM correctness, because both runtimes receive the same bytes.

## 5 · Text-region quality — the pre-registered criteria

Post-processing is the model's own **DBPostProcess** with the pinned `inference.yml` parameters
(thresh 0.3 · box_thresh 0.6 · max_candidates 1000 · unclip_ratio 1.5). Boxes are scored by
**`tests/browser/support/text-region-metrics.mjs`** — the **same code** that scored M7's floor,
extracted verbatim; M7's floor reproduces byte-identically after the extraction, and the module now
has 7 unit tests of its own.

**Deviation, stated:** 8-connected components with axis-aligned boxes, rather than OpenCV contours
and a rotated minimum-area rectangle. The fixture's text is horizontal. The effect is measured, not
assumed — see the sensitivity row.

| region | sensitive | best IoU | **PaddleOCR box convention** | coverage |
|---|---|---|---|---|
| `identifier` (14 chars) | yes | **0.427** | **0.472** | **1.000** |
| `holder-name` (12 chars) | yes | **0.365** | **0.413** | **1.000** |
| `card-title` (25 chars) | no | 0.529 | 0.611 | — |
| `field-label` (18 chars) | no | 0.374 | 0.428 | — |

| quantity | value | bar | |
|---|---|---|---|
| **criterion 2 — localisation** | 0.427 / 0.365 | IoU ≥ 0.5 each | **FAIL** |
| criterion 3 — secret coverage | 1.000 / 1.000 | ≥ 0.95 each | **PASS** |
| criterion 4 — flood | **2.98×** true text area | ≤ 3× | **PASS** |
| criterion 4 — widest single box | 0.048 of the canvas | < 0.9 | **PASS** |
| criterion 5 — no plaintext | output is a `[1,1,H,W]` float map; boxes are geometry | structural | **PASS** |
| criterion 6 — determinism | two full runs byte-identical (§6) | identical | **PASS** |
| predictions | 15 total · 7 inside the canvas · 8 outside | — | data |
| over-coverage | 0.199 of the canvas · 14 596 px² beyond the four annotated regions | — | data |

**Native and WASM produce identical boxes.** The verdict is the same under both post-processing
conventions.

### What the numbers show, recorded without changing anything

- **Every box inside the canvas is text.** The fixture draws seven strings; the detector returns
  seven boxes there, one per string. The "area beyond the annotated regions" is DB's padding around
  each line plus three real strings the ground truth does not list (`Name`, `Issued`, `2021-06-04`).
  No box lands on a region without text.
- **The localisation shortfall is structural, not a near-miss of detection.** DB's boxes are padded
  line boxes: the identifier's is 31.8 px tall against a 15 px ink box that `measureText` gives as
  ground truth. Height alone caps the IoU near 0.47 even with perfect horizontal placement, and that
  is the value measured under PaddleOCR's convention.
- **The dimensions redaction depends on pass:** every character of both secrets is covered, over-
  coverage is bounded, and nothing in the output can hold a character.

**That does not change the verdict.** Criterion 2 was pre-registered, quoted from the constitution,
and committed before any candidate ran, and the owner's instruction for this milestone was explicit:
*"Do not move the threshold."* Whether a padded-line-box detector should be judged by IoU against
tight ink boxes is a legitimate question, but it can only be settled by an owner decision that
pre-registers a revised criterion **and evaluates it on a held-out set this candidate has not been
seen on** — this fixture's result is now known and can no longer serve as an unbiased test.

## 6 · Determinism

Two complete runs of the harness — screenshot, pre-processing, native reference, WASM inference,
post-processing, scoring — were **byte-identical**: screenshot sha256, both input tensors, both WASM
output digests, both native output digests, the S-04a-1 numbers, every box and every geometry
figure. Within each run, the model was inferred **5×** on each runtime with identical output bytes.

## 7 · Performance on W1 — as measured, not generalised

Chrome for Testing, ORT Web 1.29.0 `wasm`, one thread, the pinned binary; native `onnxruntime`
1.29.0 CPU. Two runs:

| stage | run 1 | run 2 |
|---|---|---|
| model load, **WASM** | 1 253 ms | 1 195 ms |
| model load, native | 244 ms | 328 ms |
| inference **WASM**, synthetic 640×640 (median of 5) | 471 ms | 461 ms |
| inference **WASM**, realistic 640×1024 (median of 5) | **721 ms** | **717 ms** |
| inference native, realistic (median of 5) | 141 ms | 156 ms |
| DB post-processing (JS) | 60 ms | 64 ms |
| WASM linear memory after load | 29.1 MB | 29.1 MB |
| WASM linear memory after inference | **125.4 MB** | **125.4 MB** |
| artifact | 4 766 440 B | |

**An invalid first measurement, recorded rather than dropped.** The first run of the harness
recorded ~2.4 s load and ~2.5 s inference. It used cross-origin isolation plus
`--enable-blink-features=ForceEagerMeasureMemory` to reach `measureUserAgentSpecificMemory`.
`diag-latency.mjs` then showed that neither the graph's representation nor cross-origin isolation
changes latency (all four combinations: ~450–560 ms inference, ~1.17 s load), so the memory
method was replaced by observing the `WebAssembly.Memory` ORT creates — S-04a-1's quantity — and the
numbers above were taken without the flag. A first version of that hook read 0 bytes because ORT's
threaded build creates its memory in JS and imports it; the constructor is what is now observed.

**Against S-04a-1:** it recorded 234 ms inference and 474 ms create for the same input shape, in an
offscreen document. This page measures about 2× that. The representation and cross-origin isolation
are excluded as causes; the host realm, the date and machine load are not, and **no cause is
claimed**.

**In context:** the shipped perception pass is 155–273 ms in total. This detector alone would add
~0.7 s of inference per realistic frame on one thread, plus ~1.2 s once at load.

## 8 · Privacy — the architecture held, and nothing crossed

The path evaluated is region detection only:

```
RAW PIXELS → TEXT-REGION DETECTOR → [1,1,H,W] probability map → DB post-processing → BOXES + SCORES
```

- **No recognition model** exists anywhere in the harness. `PP-OCRv5_mobile_rec` was not fetched,
  converted or loaded.
- **The output cannot carry plaintext.** It is a float map; boxes are derived by geometry alone.
- **Nothing entered the product:** `git diff d9986e7 -- apps packages` is empty. The product bundle
  ships only `t1-ui-head.onnx`, with 0 occurrences of `ppocrv5`, `paddle`, `ocr_rec` or
  `recognizedString`.
- **`TextFinding` is unchanged:** `{ box, length, piiClass, ref }`, with no field for characters.
- One vault, one classifier, one redaction path, one egress authority, one click authority —
  unchanged, and the loop regression's worker, reasoner and egress scans pass 72/72.
