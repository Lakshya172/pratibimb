## The micro-overfit gate found two real bugs

Criteria were fixed in advance and **never adjusted**. Two failures, each a genuine
pipeline defect rather than a training-budget problem.

**1 — the box parameterisation could not represent its own targets.** Box loss stuck at
0.31 (mean IoU 0.69) while class loss fell to 0.077 and the CSS round trip was already
1.000. Cause: assignment marked every cell inside a box positive, but
`cx = (col + sigmoid(tx)) * stride` can only place a centre *inside that cell*. Measured:
**76% of objects span more than one cell** (mean 5.5, max 30). Fixed with
distance-to-edges → box loss **0.31 → 0.12**.

**2 — stride 16 could not see the smallest controls.** tiny(<16px) recall **0.326**,
**checkbox 0/15**, **radio 0/15**, everything else ≥0.86, and **30 of 45 misses had no
overlap at all**. My own comment had claimed a ~10 model-px checkbox "occupies most of a
16 px cell" — 10 is smaller than 16, not most of it. Fixed with stride 8; the trunk got
*smaller* (163K → 61K params). No TypeScript change: `A` is read from the tensor dims.

A third run then separated *undertrained* from *under-capacity* by holding capacity fixed —
5 of 6 criteria passed at 1500 steps, so it was convergence, and the criterion was **not**
relaxed to match.

**FINAL: PASS at 2500 steps, all six criteria.** loss 13.0% of initial · recall@0.5 0.950 ·
class 0.955 · CSS round trip 1.000 · invalid boxes 0.

## The export verification produced a false alarm

The first run reported `max |ORT − torch| = 40.4` with class channels off by 0.30 — which
reads exactly like a broken export.

It was not. `torch.onnx.export` restores the module's original training mode when it
finishes, and the module handed to it was `ExportWrapper(model)`, constructed one line
earlier and therefore defaulting to `training=True`. Restoring the wrapper propagated into
the inner model, so the reference ran with **BatchNorm on batch statistics**.

| torch mode | max abs | class channels (relative) |
|---|---|---|
| `train` (the bug) | 40.4 | 3.4e-01 |
| **`eval` (correct)** | **5.6e-03** | **1.7e-05** |

The artifact was correct all along. Fixed by calling `eval()` *after* export and asserting
it — the most expensive kind of false alarm, because the obvious response is to distrust
the artifact.

**Predictions are now generated by running the ONNX artifact**, not the torch model. The
first version measured torch while shipping ONNX; any divergence would have sat silently
between the evidence and the artifact.

## QG-05 held-out evaluation — SYNTHETIC

Threshold chosen on **dev**, test scored **once** at that threshold. Test was never swept.

| figure | value | status |
|---|---|---|
| element mAP@0.5 | **0.7955** | measured |
| element recall | **0.9229** | measured |
| grounding accuracy | **0.0547** | measured |

TP 694 · **FP 11,988** · FN 58 · invalid 0 · off-screen excluded 104

### The selection rule is defective, and this is the finding that matters

The pre-registered rule was *"max mAP@0.5 on DEV"*. It selected **0.05, the lowest
threshold on the sweep**, because mAP is almost flat across thresholds — low-confidence
false positives rank last and barely move the PR curve. Grounding accuracy is a precision
quantity and is destroyed by them:

| threshold | mAP@0.5 | recall | grounding | predictions |
|---|---|---|---|---|
| 0.05 | 0.7954 | 0.9167 | **0.0576** | 11,845 |
| 0.30 | 0.7908 | 0.9099 | 0.3155 | 2,146 |
| 0.70 | 0.5324 | 0.6640 | **0.6517** | 758 |

At the selected point the detector emits ~317 predictions per image against ~19 real
elements. **The ranking is good; the operating point is unusable.**

**No threshold was re-picked.** The test figures had already been seen by the time this
was understood, and re-selecting afterwards is threshold-fishing whatever the
justification. The corrected rule belongs to the next iteration and must be pre-registered
before test is looked at again — something like *maximise F1, or maximise grounding subject
to recall ≥ 0.90*, chosen on dev.

### Failure analysis

**`button` is the dominant failure mode** — worst AP (0.4993), worst recall (0.8168), and
a third of all false positives. The dataset has 990 button annotations against 200 each of
checkbox/radio/select/icon, so it is both the most common class and the worst performing.
The likely cause is that buttons appear at many sizes and inside cards, next to visually
identical siblings — the generator was built to make exactly that hard, and it did.

**Small objects are no longer the problem.** After the stride-8 fix, recall by size is
tiny 0.903 / small 0.979 / medium 0.964 / large 0.905. The evaluator's earlier warning that
small controls dominate has been *addressed*, not merely acknowledged — and **large objects
are now marginally worse than small ones**, which inverts the assumption the head was
originally designed around.

**Next iteration should target precision, not recall.** Recall is 0.92; precision is the
bottleneck by two orders of magnitude. That is a postprocessing and threshold problem
before it is a model-capacity problem, and increasing model size would be the wrong
response.

```bash
npm run typecheck
node tools/dataset/build-dataset.mjs --counts=120,40,40   # deterministic; hash 4bbc57de
python tools/detector/microoverfit.py --samples=16 --steps=2500

node tools/detector/regression.mjs
```

asserts `packages/` cannot import from it.
