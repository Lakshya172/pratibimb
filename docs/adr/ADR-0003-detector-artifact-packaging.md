# ADR-0003 — detector artifact packaging and runtime identity

- **Status: PROPOSED.** Not approved, not implemented, and deliberately not implementable from
  this document alone — it is architecture and evidence, not a change.
- **Date:** 2026-09-12
- **Supersedes / amends:** nothing. Extends the precedent set by
  [ADR-0001](ADR-0001-wasm-csp-and-connect-src.md).
- **Decision owner:** `ronitsaha11`

## Context

The T1 detector is `PINNED`, not `ADOPTED`, and cannot ship until adoption items 11 and 14 pass.
But *how* it would ship has never been designed, and one gap in the current architecture is worth
recording before it becomes load-bearing.

The asymmetry is the point of this ADR. `createPinnedInferenceSession(ort, model, opts)` calls
`assertOrtRuntimePinned()` and then passes `model: Uint8Array | string` straight to
`InferenceSession.create`. **The runtime verifies the interpreter and not the program.** Today
that is harmless — there is no shipped package and no adopted model. It stops being harmless the
moment either exists.

## Proposal, to be validated rather than implemented

Mirror the ORT precedent exactly, because it already works and is already reviewed.

1. **Location.** The artifact ships as an extension-local resource beside the offscreen document,
   loaded by extension URL. No CDN, no remote, no cache.
2. **Zero network, by construction.** A bundled resource cannot make a request. This is stronger
   than a policy forbidding one, and it is the same reasoning ADR-0001 used for the WASM artifact.
3. **Recording the hash.** A generated pin module in the shape of
   `packages/security/src/generated/ortPin.ts` — `{ name, bytes, sha256 }` — regenerated by the
   existing `pin:generate` flow and drift-checked by `pin:check` in CI.
4. **Runtime verification.** Recompute SHA-256 over the bytes **before** session creation and
   compare against the pin, exactly as `ortRuntimePin.ts` does for the WASM artifact.
5. **Failure behaviour: fail closed.** A mismatch throws a typed error and **no session is
   created**. It must not warn-and-continue, and it must not fall back to any other artifact.
   Byte length is checked as well, as ORT's pin already does.

### Why mirror rather than invent

ADR-0001 established two orthogonal boundaries — `connect-src` for provenance and the SHA-256 pin
for byte identity — and QG-03b/S-02a-2a-4 *measured* that both are required because the pin alone
accepts foreign-origin bytes. A bundled model needs only the byte-identity half, since provenance
is already settled by the resource being inside the package. Reusing the mechanism means reusing
its tests and its review, not writing a second integrity story that drifts from the first.

## Consequences

**Package size.** ~296 KiB against the ~26.5 MiB ORT WASM artifact already carried — roughly
**1.1%** of the existing runtime payload. Not a constraint.

**MV3 / CSP.** **No CSP change.** Model bytes are data, not script; `script-src 'self'
'wasm-unsafe-eval'` is untouched, and `connect-src` is untouched because nothing is fetched.
Bundling introduces no new MV3 surface. *This is an expectation from reading the CSP builder, not
a measured result* — it should be confirmed once a package exists.

**Privacy.** Positive, and structurally so. Local perception means visual data need not leave the
machine; a bundled model means the *model* does not phone home either. It strengthens the privacy
firewall rather than merely not weakening it.

**Licensing and provenance.** Required before shippable, and not yet assembled: the training-data
licence, the generator recipe and its hash, the training run's provenance, and the artifact's own
licence. The registry's licence column exists precisely for this and is currently unfilled for
this artifact.

## What is explicitly NOT proposed

No runtime download. No CDN. No remote fallback. No runtime model registry. No CSP relaxation. No
change to any production loader. None of those should be added, and this ADR should not be read as
softening ADR-0001 in any direction.

## Decision required

Whether to accept this as the packaging direction, so that when items 11 and 14 pass the
mechanism is already reviewed rather than improvised under delivery pressure.

**Recommended regardless of the outcome above:** the **model-identity pin is worth implementing
independently of adoption**, because the gap it closes — the runtime cannot currently tell whether
it loaded the approved artifact — exists today and is cheap to close with a mechanism the project
has already built and tested once.
