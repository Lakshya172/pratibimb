## The brief

**SIH 2026 · Problem Statement 26171 · ISRO / Department of Space**
*On-device Visual Perception for Light-weight Browser Agents*

Build a privacy-preserving vision agent that runs in the browser. A local vision model
reads the screen and decides on that basis. If visual context must be sent to a server,
the client sanitizes sensitive and personally identifying data **first** — using DOM tags
or any other method — **before any network request is made**. It must dynamically detect
and redact sensitive elements: blurring faces, blacking out passwords, masking PII. Only
anonymized, unidentifiable data may be transmitted. The server must be aware of the
redaction scheme and process data accordingly, returning actionable commands for the
browser agent to execute.

### Deliverables named in the statement
1. Client extension running in **Chrome and Firefox**, with a vision model executing locally.
2. A privacy filter — bounding-box redaction, semantic obfuscation, or masking — demonstrated clearly.
3. A server hosting an open-weight LLM/VLM that interprets sanitized context and returns
   processed data or a UI action for the client to execute.
4. One end-to-end task that visibly assists a user.

## The rubric is the specification

| Scored metric | Weight | Decided by |
|---|---|---|
| Visual context | **25%** | Shared client/server |
| PII detection | **20%** | Client |
| Redaction | **20%** | Client |
| Client resources | **20%** | Client |
| Latency | **15%** | Shared client/server |

Roughly **60%** of the score is settled entirely on the user's machine; a further 40% is
shared, and the client dominates the shared portion. Engineering effort splits roughly
**70/30** in favour of the client.

> v3.0 corrected v2.0's claim that 85% was decided client-side. Visual-context accuracy is
> measured end-to-end and depends on the server reasoning over a redacted frame, so it is
> shared, not ours alone. **Do not overstate the client share.**

**Unscored but decisive:** *task success after privacy*. A PII recall of 100% alongside a
task success rate of zero is a failed project. Both numbers go on the same slide, measured
on the same runs, as a two-row ablation: grounding accuracy and task success, redaction
off and on.

## Product thesis

**A privacy firewall that happens to power an agent.**

> Redact the value, preserve its semantic type, and let only the trusted client restore it.

The obvious build — screenshot → blur faces → send to a VLM — fails demonstrably: the
moment you black out the user's phone number, the server can no longer instruct the agent
to type the phone number. Privacy has eaten the product.

PratiBimb resolves this with a **redaction manifest** and a **memory-only vault**. Every
sensitive span becomes a typed placeholder — `<PII:PHONE:1>` — carrying the *shape* of the
data without its *content*. The server plans in placeholders. The client substitutes real
values at the instant of execution.

**The server is functionally complete and structurally blind.**

## Five principles (dossier §3)

1. **The client never trusts the server.** Server output is a proposal — validated against
   an allowlist locally, and re-validated against the live page, before anything executes.
2. **Fail closed.** When a detector errors, times out, or disagrees, the union of masks
   wins. An over-mask costs nothing, because re-hydration restores the capability. A
   missed Aadhaar number ends the demo.
3. **Page content is data, never instruction.** Text scraped from a website cannot direct
   the agent. Only the user's stated goal can.
4. **Measure before optimising.** The evaluation harness is built in week two, not week six.
5. **Secrets cross as references; everything else crosses as itself.** The server may
   reference a vault token, and may propose a plain literal for a field holding nothing
   sensitive. What it may never do is emit a string the vault already contains — that
   would mean it reconstructed a secret it was never given. The client decides which of
   those three cases it is looking at, on every action.

## What we refuse to claim

- We do **not** claim k-anonymity or differential privacy.
- A determined adversary correlating quasi-identifiers across many sessions is **outside
  our threat model**, and we say so rather than implying otherwise.
- We do **not** assert cross-browser parity — we **publish** it
  (`agentos/registry/feasibility-matrix.md`).
- Zero residual leakage is an **objective**. It goes on the title slide only once the
  harness has demonstrated it across the full evaluation set.
- Every latency figure is a **budget** until the harness replaces it with a measurement.
